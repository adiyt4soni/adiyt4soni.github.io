Vex

A personal assistant that runs on an open-weight model on my own laptop. What it may do is decided in code, not in its prompt, so it can't send, delete or read restricted files without my approval. From 13 to 19 October every change Claude Code wrote was reviewed by Codex before I decided whether it merged.

What it does

Merged and working on the main branch:

  • a daily briefing built from the calendars I've authorised, with no model involved;
  • a chat that keeps conversations for 30 days;
  • encrypted backups with a tested restore;
  • a permission gate that every action passes through.

The runtime talks only to a model on my own machine.

On a frozen release candidate, built and tested but not merged: weather and London journey lookups (opt-in), on-device voice, a few Mac actions such as opening an app, and read-only Google access with draft creation, which isn't yet connected to my account. Sending email is blocked in code: the only Gmail endpoint Vex may call is draft creation (the Google permission itself would technically allow sending). Persistent memory and an approval queue exist on separate branches and stay off until reviewed.

Why I built it

I wanted an assistant for briefings, notes and calendar that doesn't hand my personal files to a cloud model, and that never claims it did something it didn't. That second requirement turned out to be the hard one. A lot of the later work is about honest reporting: the assistant shouldn't say 'sent' when nothing was sent.

My role and the AI's role

  • Me: the charter and constraints; what comes first (the daily briefing, then encrypted backups); which local actions are allowed (open an app, yes; quit an app or open a URL, no); keeping the knowledge module disabled after Codex rated it not ready; requiring every review to leave a verifiable record; and every merge.
  • Claude Code: wrote nearly all the code, across ten parallel lanes, each in its own working copy.
  • Codex: wrote an independent first foundation that was merged in, and reviews every change.

The bugs were found by Codex and by Claude's own audits, not by me. My contribution is the rules and the decisions.

Approach

  • Permissions in code. Every tool has a fixed action class, looked up by its name and never by what the model says. Read-only actions run; consequential ones need approval; the most dangerous are denied outright. Tests prove that no setting and no injected text can escalate a class.
  • A never-read list. Restricted personal documents, health data, keys and credential files are denied by path, and checked by the file's identity on disk so a renamed link can't bypass the rule.
  • Prompt-injection tests with controls. Five injection attacks run against the real model. Two model-free controls run first: one proves the gate blocks a forced dangerous call, and the other proves the test can detect a breach at all. The gate held 5 of 5 in September and again in October.
  • Plain code at the boundary. Where the model corrupted file paths and special characters about 10% of the time, normalisation moved into plain code at the tool boundary, and tools that read files take no path from the model.

What the reviews caught

  • Tests that couldn't fail. The first Codex review, on 6 Sep, found that Claude's permission tests passed even with the gate disabled, because the fake handler crashed before its check ran. It also found credential-shaped values leaking into logs. Both are fixed and locked in by regression tests named after the review.
  • A privacy bypass in a fix. A later review found that Claude's own fix let an unverified place name reach the public transport lookup. It was reproduced with a synthetic probe and fixed.
  • A leak in the review setup itself. In October, Claude found that Codex's memory feature had imported earlier Claude transcripts containing restricted personal details, so that memory was being fed to Codex during reviews. I switched the import off. The review tool now turns Codex memory off on every run, checks that it really is off before starting, and records the result.

How it was checked

Each review is a fixed command: Codex runs read-only against a pinned commit, with a written brief to attack specific claims. A script then confirms that Codex's own session file exists, matches the request and shows a completed task, before the review counts. Between 13 and 19 Oct there were 129 review records: 94 completed and 35 incomplete, mostly from usage limits. 71 of the completed reviews ended with a negative verdict (not mergeable, not fixed, changes requested), counting re-reviews of fixes. From 20 Oct I moved to one review campaign at the end of the build.

The model bake-off fixed nine pass criteria before any result and ran five configurations in two rounds, forward and reversed. The current model passed every quality test but failed the memory limits; a smaller model fitted in memory but failed quality. Verdict: no switch.

Limits

  • Small merged core. The main branch holds about 4,000 lines; the release candidate about 20,000, unmerged. Much of a week's volume was process (reviews of reviews) rather than product.
  • Not independent in every sense. A second model is a separate review, not a guarantee. Claude chooses what to send and wrote the verification script, and Codex's sandbox can't run the full test suite.
  • Not yet accepted. I haven't recorded acceptance testing on my real data, and the last integrated review of the release candidate is incomplete.
  • No off-device copy. No remote copy of the repository exists beyond local encrypted backups.

Safe demonstration

Vex can print its permission table, and its injection controls run against a throwaway home folder with scripted responses, so no personal data is involved. A recorded demo of those is planned; until it exists, this page shows the method only.
