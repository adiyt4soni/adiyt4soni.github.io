What it does

Most of the goals listed under 'Why I built it' already exist as tested code:

  • Daily briefing from the calendars I've authorised, built without a model so it can't make anything up.
  • Chat that keeps conversations for 30 days, on a model running on my own machine.
  • Voice: on-device speech recognition and a local voice that runs in a sandboxed process with no network.
  • Mac actions: open or hide an app, show a file, set the volume. Quitting apps and opening links are deliberately excluded.
  • Google: reads Gmail, Drive, Docs and Sheets and creates email drafts. Sending is blocked in code: the only Gmail action it may take is creating a draft.
  • Lookups: weather and London journeys, opt-in.
  • Encrypted backups with a tested restore.

Also built: answers from my notes and documents (citing the note and date, keyword search by design), memory, and an approval queue for calendar and reminder changes. Those three stay switched off until their reviews pass.

The foundation is merged. The rest is in a frozen release candidate of about 20,000 lines with about 1,760 tests, which I'm testing on my own data now. Still to come from the goal list: the wake word, screen control as a fallback, file organising, photo search, delegation to other agents, and approved email sending.

Why I built it

I want Vex to be a calm, capable chief of staff in the spirit of JARVIS. I want to be able to talk to it like a person, and for it to:

  1. Know my day. An accurate briefing from my calendars, with recurring events and time zones handled correctly and nothing made up.
  2. Hold a real conversation and remember what matters (people, projects, preferences, goals), in a memory I can inspect, correct, export and delete.
  3. Speak and listen, with a natural British voice and push-to-talk first, then a wake word.
  4. Operate my Mac: open apps, websites and media, organise files without ever deleting anything, and search my photos, with direct integrations first and screen control only as a fallback.
  5. Handle email properly: read first, and send only a message I've approved word for word.
  6. Delegate. Hand bigger jobs to specialist agents such as Claude Code or Codex, have a second agent check the first agent's work, and report what was verified and what wasn't.
  7. Stay out of the way: a small animated presence near the top of the screen, light enough to run alongside my usual apps on a 24 GB laptop.

Underneath all of it, private information never reaches a cloud service unless I approve a specific, permission-controlled step.

Why it matters to me

I wanted an assistant for briefings, notes and calendar that doesn't hand my personal files to a cloud model, and that never claims it did something it didn't. That second requirement turned out to be the hard one. A lot of the later work is about honest reporting: the assistant shouldn't say 'sent' when nothing was sent.

My role and the AI's role

  • Me: the charter and constraints, what comes first (the daily briefing, then encrypted backups), which local actions are allowed (opening an app, yes; quitting an app or opening a URL, no), keeping the knowledge module disabled after Codex rated it not ready, a verifiable record for every review, and every merge.
  • Claude Code: wrote nearly all the code, across ten parallel lanes, each in its own working copy.
  • Codex: wrote an independent first foundation that was merged in, and reviews every change.

Most bugs were found by Codex and Claude's own audits. I decided which to fix and in what order. AI writes the code. I read it through in VS Code with GitHub Copilot, adjust it, and check it with separate tools (automated tests and a second AI model's review) so I know it does what Claude Code says it does.

How it works

  • Permissions in code. Every tool has a fixed action class, looked up by its name and never by what the model says. Read-only actions run, consequential ones need approval, and the most dangerous are denied outright. Tests prove that no setting and no injected text can escalate a class.
  • A never-read list. Restricted personal documents, health data, keys and credential files are denied by path, and checked by the file's identity on disk so a renamed link can't bypass the rule.
  • Prompt-injection tests with controls. Five injection attacks run against the real model. Two model-free controls run first: one proves the gate blocks a forced dangerous call, and the other proves the test can detect a breach at all. The gate held 5 of 5 in September and again in October.
  • Plain code at the boundary. Where the model corrupted file paths and special characters about 10% of the time, the normalising now happens in plain code at the tool boundary, and tools that read files take no path from the model.

What I caught and changed

  • Tests that couldn't fail. The first Codex review, on 6 Sep, found that Claude's permission tests passed even with the gate disabled, because the fake handler crashed before its check ran. It also found credential-shaped values leaking into logs. Both are fixed and locked in by regression tests named after the review.
  • A privacy bypass in a fix. A later review found that Claude's own fix let an unverified place name reach the public transport lookup. It was reproduced with a synthetic probe and fixed.
  • A leak in the review setup itself. In October, Claude found that Codex's memory feature had imported earlier Claude transcripts containing restricted personal details, so that memory was being fed to Codex during reviews. I switched the import off. The review tool now turns Codex memory off on every run, checks that it really is off before starting, and records the result.

How it was checked

Each review is a fixed command. Codex runs read-only against a pinned commit, with a written brief to attack specific claims. A script then confirms that Codex's own session file exists, matches the request and shows a completed task, before the review counts. Between 13 and 19 Oct there were 129 review records: 94 completed and 35 incomplete, mostly from usage limits. 71 of the completed reviews ended with a negative verdict (not mergeable, not fixed, changes requested), counting re-reviews of fixes. From 20 Oct I moved to one review campaign at the end of the build.

The model bake-off fixed nine pass criteria before any result and ran five configurations in two rounds, forward and reversed. The current model passed every quality test but failed the memory limits, and a smaller model fitted in memory but failed quality. The verdict was no switch.

Where it is now

  • Testing. I'm accepting the release candidate on my own data and fixing the bugs it turns up, before it becomes my everyday assistant.
  • Notes search, memory and approvals stay off until their reviews pass.
  • A second model isn't a guarantee. Codex's reviews are a separate check, not an independent one: Claude chooses what to send and wrote the verification script, and Codex's sandbox can't run the full test suite.
  • No off-device copy of the code yet beyond local encrypted backups.

A safe demonstration

Vex can print its permission table, and its injection controls run against a throwaway home folder with scripted responses, so no personal data is involved. A recorded demo of those is planned; until it exists, this page shows the method only.
